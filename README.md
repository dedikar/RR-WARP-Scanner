# RR WARP Scanner

**Поиск рабочих эндпоинтов Cloudflare WARP прямо на роутере — с проверкой, что
через них действительно работает Telegram.**

[![Platform](https://img.shields.io/badge/OpenWrt-24.10%20%7C%2025.12-blue)](#требования)
[![Package](https://img.shields.io/badge/package-luci--app--rrws-green)](#установка)
[![Engine](https://img.shields.io/badge/engine-Go%2C%20userspace%20AmneziaWG-orange)](#как-это-работает)
[![License](https://img.shields.io/badge/license-Apache--2.0-lightgrey)](LICENSE)

LuCI-приложение для роутеров на OpenWrt. Сканирует пул эндпоинтов Cloudflare
WARP, проверяет каждый настоящим туннелем, измеряет задержку и потери, пробует
дотянуться до дата-центров Telegram — и отдаёт готовый `.conf` для лучшего.

Движок — статический Go-бинарник с userspace-реализацией AmneziaWG. Ядерный
модуль, `/dev/net/tun` и `ip link` не используются вообще.

## Зачем это нужно

Cloudflare WARP работает не везде одинаково. Из России часть эндпоинтов
недоступна, часть отвечает на handshake, но не пропускает данные, часть
пропускает всё, кроме Telegram. Проверить это вручную невозможно: в пуле
несколько тысяч адресов.

Это приложение прогоняет пул с роутера, отбрасывает мёртвые и «оборванные»
эндпоинты, отдельно проверяет доступность Telegram и даёт готовый конфиг для
тех, что реально работают.

**Основное — поиск эндпоинтов.** Обычный пинг показывает задержку до эндпоинта
WARP, а не то, доедет ли через него трафик до нужного сервиса: адрес может
отвечать за 40 мс и при этом не пропускать данные. Поэтому к сканированию
добавлена **проверка Telegram** — не как самоцель, а как практический критерий
того, что туннель действительно пригоден.

## Что умеет

- **Скан прямо на роутере** — внешний компьютер не нужен, ничего никуда не
  отправляется.
- **Проверка Telegram** через MTProto по всем пяти дата-центрам: `TG 5/5` значит
  доступны все, `TG blocked` — ни один.
- **Готовый `.conf`** для каждого эндпоинта, с параметрами обфускации.
- **Замер скорости** внутри туннеля (по желанию).
- **Определение «оборванных» туннелей** — тех, где handshake проходит, а данные
  DPI рвёт. Такие помечаются и никогда не выбираются лучшими.
- **Фильтр «только с Telegram»** — оставить лишь те эндпоинты, через которые
  Telegram работает.
- **Сортировка** по узлу, пингу, задержке в туннеле, скорости и Telegram, в обе
  стороны.
- **Управление аккаунтом WARP** из интерфейса: регистрация, перерегистрация,
  удаление. Аккаунт переживает перезагрузку и прошивку.
- **Работает без ядерного модуля** — не требует `kmod-amneziawg`, не трогает
  сетевые интерфейсы роутера.

## Требования

Роутер на **OpenWrt 24.10** или **25.12**, архитектура **aarch64** (проверено на
mediatek/filogic, Cortex-A53).

Зависимости, все из штатных репозиториев OpenWrt:

```
libc, ca-certificates, luci-base, rpcd-mod-ucode
```

`kmod-amneziawg`, `amneziawg-tools`, `jq` и `curl` **не нужны** — в отличие от
предыдущей версии приложения.

## Установка

Скачайте пакет со страницы [Releases](../../releases) и установите:

**OpenWrt 24.10 (opkg):**

```sh
opkg install --force-reinstall /tmp/luci-app-rrws_<версия>_all.ipk
```

**OpenWrt 25.12 (apk):**

```sh
apk add --allow-untrusted /tmp/luci-app-rrws-<версия>.apk
```

Через веб-интерфейс: **System → Software → Upload Package**. После установки
откройте страницу с **Ctrl+F5** — LuCI кэширует карту меню, и без сброса кэша
пункт может не появиться.

Приложение появится в **Services → RR WARP Scanner**.

## Использование

**1. Зарегистрировать аккаунт.** При первом входе нажмите «Зарегистрировать
WARP». Если API Cloudflare недоступен напрямую, движок сам попробует обходные
пути — релей, затем собственный туннель. Ход регистрации виден в логе под
кнопкой, включая причину сбоя, если он будет.

Занимает до минуты. Регистрация через туннель — нормальный случай, а не ошибка:
на сетях, где API заблокирован, это единственный способ.

**2. Настроить скан.** По умолчанию уже выставлено разумное:

| Поле | По умолчанию | Что значит |
|---|---|---|
| Хостов на подсеть | 100 | адресов из каждой из 14 подсетей, 1–256 |
| Таймаут | 3 с | ожидание handshake |
| Потоков | 64 | параллельных туннелей (измеренный оптимум) |
| Протокол | AmneziaWG | обфусцированный; `WireGuard` на этой сети не работает |

**3. Нажать «Найти тоннели».** Скан на 1400 адресов занимает около трёх минут.

**4. Забрать результат.** У каждой строки — «Скопировать .conf» и «Показать
.conf». Кнопка «Скачать всё .txt» отдаёт конфиги всех найденных разом.

### Что означают галочки

| Галочка | По умолчанию | Действие |
|---|---|---|
| Проверять Telegram | вкл | пробует MTProto по 5 дата-центрам |
| Оставить только с рабочим Telegram | выкл | убирает из результата всё остальное |
| Измерять TUN PING / LOSS | вкл | задержка и потери внутри туннеля, детект обрывов |
| Отображать только стабильные | вкл | прячет оборванные и с потерями |

Поле **«Эхо-пакетов (TUN PING)»** задаёт длину проверки на обрыв: движок шлёт
столько пакетов с интервалом 200 мс и считает туннель оборванным, если ответ
прекратился на середине. Больше пакетов — ловит более поздние обрывы, но дольше:
10 пакетов это 2 секунды на каждый эндпоинт.

## Проверка Telegram

Движок открывает внутри туннеля соединение с пятью дата-центрами Telegram и
отправляет MTProto-запрос `req_pq_multi` — тот же, что посылает сам клиент при
подключении. Учитывается, сколько ДЦ ответили и за какое время.

| Бейдж | Значение |
|---|---|
| `TG 5/5` | отвечают все пять — приложение подключится с любого аккаунта |
| `TG 3/5` | отвечает часть: аккаунты, привязанные к недоступным ДЦ, не подключатся |
| `TG blocked` | ни один не ответил — Telegram через этот эндпоинт не работает |

Замеры на реальной сети: 390–2196 мс. Это нормальный диапазон для MTProto
поверх WARP, а не признак плохого эндпоинта, поэтому для Telegram используется
своя цветовая шкала.

## Сортировка и подсветка

Под сводкой — кнопки сортировки:

```
Сортировка:  [По умолчанию]  [Скорость]  [Узел]  [Пинг]  [Туннель]  [Telegram]
```

**По умолчанию** — рекомендованный порядок движка: сначала эндпоинты с рабочим
Telegram, затем стабильные, затем с наименьшей задержкой в туннеле. Повторный
клик по активной кнопке меняет направление, стрелка `↑`/`↓` показывает текущее.

Метка **ЛУЧШИЙ** следует за сортировкой: при сортировке по пингу она стоит на
эндпоинте с наименьшим пингом, по скорости — на самом быстром. При сортировке по
узлу метки нет: код узла это название, а не качество.

**Подсветка значений:**

- код узла — янтарный;
- задержка — зелёный до 80 мс, жёлтый до 150, красный выше;
- Telegram — зелёный до 400 мс, жёлтый до 1000, красный выше (своя шкала).

Неизмеренные значения всегда внизу списка, независимо от направления
сортировки: «нет данных» не должно выглядеть как лучший результат.

## Как это работает

```
LuCI-страница
   └─ rpcd (ucode) ── /usr/bin/rrws scan --json --progress FILE
                        ├─ Фаза 1: какие порты WARP открыты в этой сети
                        ├─ Фаза 2: туннель до каждого адреса, замер, метаданные
                        ├─ Проверка Telegram через туннель (если включена)
                        └─ Замер скорости (если включён)
```

Движок держит **по одному userspace-туннелю на поток** и переиспользует его для
десятков эндпоинтов, меняя только адрес через UAPI. Никаких сетевых интерфейсов
не создаётся, `ip link` и `ip rule` не вызываются, состояния роутера работа не
касается.

**Почему AmneziaWG, а не WireGuard.** На целевой сети обычный WireGuard проходит
handshake и не пропускает данные: DPI рвёт соединение после установления. Это
измерено — одна и та же подсеть под двумя протоколами:

| Протокол | Рабочих | Состояние | Telegram |
|---|---|---|---|
| `wg` | 5/12 | все оборванные, потери 90–100 % | 0 ни на одном ДЦ |
| `awg` | **12/12** | без обрывов | **4 из 12 достигают всех 5 ДЦ** |

Поэтому AmneziaWG — протокол по умолчанию.

## Блок «Дополнительно»

Настройки обфускации и охвата скана. **По умолчанию трогать ничего не нужно.**

### Jc / Jmin / Jmax

Параметры обфускации AmneziaWG. Каждый UDP-пакет WireGuard начинается с байта
типа сообщения (`1` — handshake, `2` — ответ, `4` — данные), и именно по нему
DPI опознаёт протокол. AmneziaWG прячет его, отправляя перед настоящим пакетом
мусорные:

- **Jc** — сколько мусорных пакетов отправить;
- **Jmin / Jmax** — минимальный и максимальный размер мусора в байтах.

По умолчанию `6 / 10 / 50`. Менять имеет смысл, только если провайдер начал
резать и эту схему.

Подбирают такие значения **не на глаз, а подкомандой `find-junk`** — и её
намеренно нет в интерфейсе. Это цикл без ограничения на число попыток: движок
генерирует случайный набор, прогоняет полный скан и повторяет, пока не поднимется
заданная доля эндпоинтов или пользователь не прервёт. В терминале это
самоограничивается тем, что человек смотрит на вывод; в веб-интерфейсе это была
бы кнопка, которая молотит роутер часами. Плюс результат у неё не список
эндпоинтов, а набор параметров.

```sh
# перебирать наборы, пока 50 % выборки не поднимется
/usr/bin/rrws find-junk -a /etc/rrws-account.json -n 12 -threshold 50
```

### Генерировать I1

**I1** — *init packet*, первый пакет вместо обычного handshake. Без него
используется встроенный — захардкоженный DNS-запрос к `icloud.com`. Список
заставляет движок сгенерировать I1 под другой протокол:

| Вариант | Подо что маскируется |
|---|---|
| (не генерировать) | встроенный запрос к icloud.com |
| QUIC | ClientHello от QUIC-соединения |
| DNS | DNS-запрос с padding-записью EDNS0 |
| SIP | пакет SIP-телефонии |
| STUN | STUN-пакет (WebRTC) |
| случайный | любой из четырёх, выбранный жребием |

Смысл появляется, когда сеть придирается именно к содержимому.

**I1-sni** — хост, которым прикидывается сгенерированный I1 (работает только
вместе с генерацией). Пусто — движок берёт один из четырёх: `www.apple.com`,
`www.google.com`, `www.microsoft.com`, `cdn.jsdelivr.net`.

**Свой I1** — ручной ввод init packet целиком. Заполненное поле перебивает и
встроенный, и генерацию. Значение `none` означает «не отправлять вообще».

### Только порт

Cloudflare WARP отвечает на четырёх основных UDP-портах: **2408, 500, 1701,
4500**. Обычный скан сначала пробует их, находит открытые и дальше работает с
ними; если ни один не открылся, добавляет ещё полсотни резервных.

Поле закрепляет **один конкретный порт** и полностью пропускает фазу 1: быстрее,
но без гибкости — если этот порт закрыт, рабочих эндпоинтов не будет вовсе.
`0` — автоматический режим.

### Полный перебор

По умолчанию берётся столько адресов из подсети, сколько указано в «Хостов на
подсеть». Галочка игнорирует это поле и берёт **все 256 адресов каждой подсети**:

- IPv4: 14 подсетей × 256 = **3584 адреса**;
- IPv6 (если включён следующий пункт): 2 подсети × 256 = **512 адресов**.

Дольше и без гарантии, что найдётся что-то лучше. Последний вариант, когда
обычный скан ничего не дал.

### Использовать IPv6-пул

Переключает скан на IPv6-пулы (`2606:4700:d0::/48`, `2606:4700:d1::/48`).
Некоторые провайдеры дают IPv6, но режут IPv4 к Cloudflare — это запасной обход.
Нужен рабочий IPv6 у роутера.

## Узел и страна — в чём разница

Два поля, которые легко перепутать:

- **Узел (NODE)** — точка входа, куда вы подключаетесь. IATA-код города:
  ARN — Стокгольм, FRA — Франкфурт, AMS — Амстердам, DME — Москва.
- **Страна (COUNTRY)** — откуда внешние сайты видят ваш трафик. Определяется
  маршрутизацией аккаунта WARP, **а не** узлом входа.

Можно войти через Варшаву и всё равно «выходить» из РФ — это норма, а не ошибка.

Узел при этом влияет на фильтрацию: трафик через московский узел (DME)
фильтруется внутри РФ, через зарубежные — нет. Поэтому DME исключён по умолчанию.

Если цель — чтобы сайты видели не РФ, выбор эндпоинта не поможет. Нужна другая
точка входа, например VPS за рубежом.

## Что переживает перезагрузку

| Файл | reboot | sysupgrade |
|---|---|---|
| `/etc/rrws-account.json` — аккаунт WARP | да | да |
| `/etc/rrws-settings.json` — настройки | да | да |
| `/etc/rrws-last-result.json` — результат скана | да | да |
| `/tmp/rrws_result.json` — текущий запуск | нет | нет |
| `/tmp/rrws-state/` — логи и прогресс | нет | нет |

Результат сохраняется сразу по завершении скана и после перезагрузки страница
отдаёт его же. Настройки формы сохраняются при каждом запуске.

## Диагностика

Пакет помечен `Architecture: all` (он в основном скрипты), но несёт бинарник под
**aarch64**. На роутере с другим процессором установка пройдёт, файл появится, а
движок не запустится — внешне это выглядит как «пакет ничего не делает».

Проверка встроена в три места.

**1. Сразу после установки** — `postinst` пишет в системный лог:

```sh
logread | grep rrws
# rrws: installed: router arch aarch64_cortex-a53, engine runs: yes
```

Если движок не запустился, там будет `engine runs: no` и причина.

**2. Кнопка «Информация»** рядом с блоком аккаунта — собирает отчёт: версии,
архитектура, права, свободное место, последние строки логов. Кнопка видна только
на чужом железе (проверяется OUI `24:0F:5E`).

**3. Вручную:**

```sh
/usr/bin/rrws version                  # отвечает ли движок
ubus call luci.rrws scanStart          # текст ошибки прямо в ответе
cat /tmp/rrws-state/scan.log           # что сказал движок
cat /tmp/rrws.rpc.log                  # что и куда запускал бэкенд
```

## Сборка

Нужен Linux с Go (в WSL годится). Windows-тулчейн не подойдёт: собранный им
бинарник падает на роутере с `SIGILL`.

```bash
# версия берётся из version.txt, собирается .ipk
./build.sh
# явная версия
./build.sh 0.3.1-r40
# оба формата (ipk + apk)
./build.sh both
```

Схема версий: `x.y.z-rN`, ревизия растёт до 99, затем увеличивается `z`.

### Размер

Движок — статический Go-бинарник с userspace-netstack, это основная часть веса.
UPX-сжатие встроено в `build.sh` и применяется **к бинарнику до упаковки**: ipk —
это gzip-архив, сжимать уже сжатое бессмысленно.

| | бинарник | пакет |
|---|---|---|
| без UPX | 12.6 МБ | 4.84 МБ |
| с UPX | 3.25 МБ | **3.40 МБ** |

Собрать без сжатия — `NO_UPX=1 ./build.sh`.

### Потоки (замерено)

На роутере с 2 ядрами Cortex-A53, полный пул, Telegram и скорость выключены:

| потоков | время | нагрузка |
|---|---|---|
| 8 | 68.6 с | 1.39 |
| 32 | 28.0 с | 1.55 |
| **64** | **21.9 с** | **1.26** |
| 128 | 25.1 с | 2.06 |
| 256 | 25.2 с | 3.00 |

Плато около 64: дальше время не улучшается, а нагрузка растёт. Потолок в
интерфейсе выставлен по этому замеру.
