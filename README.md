# Форк warpscout-tg для роутера RouteRich (OpenWrt 24.10 / 25.12)

LuCI-приложение **RR WARP Scanner** ищет рабочие эндпоинты Cloudflare WARP
**прямо на роутере** и отбирает те, через которые действительно работает
Telegram. Движок — Go-бинарник (userspace AmneziaWG), ядро и `kmod-amneziawg`
не используются.

## Имя пакета

Пакет называется **`luci-app-rrws`** — то же имя, что у предыдущего приложения,
и без суффикса NG, который носили промежуточные сборки. Переименование сквозное:
имя пакета, ubus-объект `luci.rrws`, бинарник `/usr/bin/rrws`, бэкенд
`/usr/share/rpcd/ucode/luci.rrws`, страница `…/view/rrws/scan.js` и файлы
состояния `/etc/rrws-*.json`, `/tmp/rrws-state/`.

На роутере, где стояла сборка под старым именем, остатки снимаются один раз
скриптом `tests/migrate_rrwg_to_rrws.py`: он удаляет прежний пакет, переносит
аккаунт WARP на новые имена (роутер сохраняет свою регистрацию, а не заводит
новую) и ставит новый IPK. На чистой установке он не нужен.

## Зачем переписали

Предыдущее приложение (`luci-app-rrws`, папка `C:\Users\dedikar\warp`) строило
ядро AmneziaWG заново на каждый эндпоинт: `ip link del` → `ip link add` →
`setconf` → `ip rule add`. Обфускацию нельзя применить на живой интерфейс (на
этом ядре это даёт kernel oops), поэтому каждый пробник стоил полной пересборки
интерфейса. На 2-ядерном Cortex-A53 это упиралось в 50 воркеров, а на реальной
сети приложение находило **0 рабочих эндпоинтов**.

Этот движок держит по userspace-туннелю на воркер и меняет только endpoint
через UAPI — ядерных интерфейсов нет вообще.

## Ключевая находка: нужен `-p awg`, а не `-p wg`

Апстрим warpscout по умолчанию использует чистый WireGuard (`-p wg`). На сети
этого роутера такой туннель поднимает handshake и **дальше не пропускает
данные** — DPI рвёт его. Замер на одном и том же `/24` с одним аккаунтом:

| Протокол | Рабочих | Состояние | Telegram |
|---|---|---|---|
| `wg` | 5/12 | все `torn`, потери 90-100% | 0 ни на одном ДЦ |
| `awg` | **12/12** | без обрывов | **4 с 5/5 ДЦ** |

Поэтому в форке `defaultProto = protoAWG` (`engine/warp.go`). Возврат на `wg`
означает приложение, которое ничего не находит.

## Результат приёмки

`tests/acceptance.py` на тестовом роутере (12 хостов на подсеть):

- **14 из 14 эндпоинтов рабочих**, потерь нет
- **9 с полным Telegram 5/5**, остальные 3/5 (частично — часть аккаунтов не подключится)
- Скан занимает ~12 секунд

## Интерфейс

- **Тест скорости** — отдельная секция с полем «Эндпоинтов» (1–40). Замер идёт
  после скана, по одному эндпоинту за раз; результат виден в строке эндпоинта
  («скорость 38.5 Мбит/с»). Неизмеренные помечены как неизмеренные, а не «0».
- **Валидация полей** — у каждого числового поля видна подсказка с диапазоном,
  при выходе за границы под полем появляется ошибка и красная рамка, кнопка
  «Найти тоннели» блокируется. Бэкенд дополнительно подрезает значения.
- **Лог запуска** отвечает на вопрос «что и куда пошло»:
  `proto=awg perSubnet=6 total~6 jobs=8 timeout=3 tg=on tunPing=on speed=top10 port=auto targets=8.34.70.0/24`
  и отдельной строкой `pid=… out=… log=…`.
- **Регистрация с видимым ходом.** Регистрация аккаунта WARP идёт до трёх минут
  и проходит цепочку: API напрямую → релей → WARP-туннель (сначала `awg`, потом
  `wg`). Пока она идёт, под кнопкой раскрывается панель с логом движка, а при
  сбое там же видна его причина — раньше в этом месте был только счётчик секунд,
  и при неудаче страница сообщала «не завершилась» без единой зацепки.

  На живой сети это выглядит так (реальный лог с роутера, когда API Cloudflare
  заблокирован провайдером):

  ```
  00:39:08  engine  Checking Cloudflare API availability...
  00:39:11  engine  API unreachable directly
  00:39:11  engine  Registering through the relay (https://edge-client-api.vercel.app)...
  00:39:56  engine  relay: Post "...": Client.Timeout exceeded while awaiting headers
  00:39:56  engine  Registering through a WARP tunnel (pass -proxy to use a proxy instead)
  00:39:56  engine  probing awg (default iCloud I1) endpoints...
  00:40:03  engine  Registered fresh WARP account -> /etc/rrws-account.json
  ```

  То есть при заблокированном API аккаунт всё равно выдаётся — через
  userspace-туннель. Отдельный прокси для этого не нужен: движок поднимает
  туннель сам, а ядерный `kmod-amneziawg` для этого не требуется.
  Строки регистрации попадают и в общий лог страницы, вперемешку со строками
  скана и бэкенда.

- **Шапка как в предыдущем пакете**: заголовок, строка с версией, таблица
  «Аккаунт WARP | ЗАРЕГИСТРИРОВАН». Рядом с блоком аккаунта — плитка-баннер
  (логотип + «Информация») со ссылкой на вендорскую страницу; показывается
  **только** когда `deviceCheck` не находит OUI RouteRich (24:0F:5E), то есть на
  своём роутере она скрыта, а на чужом железе видна.
- **Все флаги движка** доступны со страницы: протокол, Telegram, TUN PING/LOSS,
  стабильность, порт, IPv6, спидтест, `Jc/Jmin/Jmax`, генерация `I1`
  (quic/dns/sip/stun/random), `I1-sni`, полный перебор.
- **Исключения и фильтры узлов — выпадающие списки с чекбоксами** (подсети,
  «Исключить узлы», «Только узлы»). Заголовок показывает выбранное, например
  `DME, ARN (2)`. Список узлов бэкенд собирает из достигнутых этим роутером
  кодов плюс известный набор WARP-узлов, DME первым.
- **Колонка Telegram** с бейджами `TG 5/5` / `TG 3/5` / `TG blocked`; лучшим
  выбирается первый нетронутый **и** с полным Telegram.
- **Сводка с узлами** под счётчиком найденного: `AMS ×91  ARN ×87  FRA ×27` —
  коды узлов, на которые попали эндпоинты, по убыванию количества. Считается по
  показанному списку, поэтому после фильтра «только стабильные» описывает ровно
  то, что видно на экране.
- **Сортировка результатов** пятью кнопками: «По умолчанию» (рабочий Telegram →
  стабильность → пинг в туннеле), «Узел», «Пинг», «Туннель», «Telegram».
  Повторный клик по активной кнопке меняет направление, стрелка `↑`/`↓` в
  подписи показывает текущее. Метка «ЛУЧШИЙ» привязана к данным, а не к позиции,
  поэтому при сортировке по убыванию пинга она оказывается в середине списка —
  где и находится лучший эндпоинт.
- **Подсветка значений**: код узла — янтарный, задержки — по полосам (зелёный до
  80 мс, жёлтый до 150, красный выше). Telegram меряется по своим полосам
  (зелёный до 400 мс, жёлтый до 1000), потому что MTProto поверх WARP — это
  400–600 мс в норме, и общая шкала красила бы всё в красный.
- **Кнопка «Свернуть/Развернуть»** рядом со счётчиком найденного — чтобы
  длинный список результатов не занимал весь экран.
- **Кнопки «Копировать»** у ID и PrivateKey аккаунта.
- **Мобильная раскладка**: ниже 700px карточка результата складывается в две
  строки (данные сверху, кнопки под ними), подписи полей сжимаются до 40 %
  ширины. Горизонтальной прокрутки нет.

## Блок «Дополнительно»: что означают его пункты

Это настройки обфускации AmneziaWG плюс три параметра охвата скана. **По
умолчанию ничего из этого трогать не нужно** — значения подобраны так, чтобы
работать на обычной сети.

### Jc / Jmin / Jmax

Параметры обфускации AmneziaWG.

Каждый UDP-пакет WireGuard начинается с байта типа сообщения: `1` — handshake
initiation, `2` — response, `4` — data. Именно по этому байту DPI и опознаёт
протокол. AmneziaWG прячет его, отправляя перед настоящим пакетом мусорные:

- **Jc** — сколько мусорных пакетов отправить перед реальным;
- **Jmin** / **Jmax** — минимальный и максимальный размер этого мусора в байтах.

По умолчанию `6 / 10 / 50` — то же, что у апстрима warpscout, и то же, что
прописано в WARP-интерфейсе. Менять имеет смысл, только если провайдер начал
резать и эту схему; подбирают такое не на глаз, а подкомандой `find-junk`
(в UI её нет — это отдельный режим движка).

### Генерировать I1

**I1** — *init packet*, первый пакет, который AmneziaWG отправляет вместо
обычного handshake. Если его не задать, используется встроенный:

```
<r 2><b 0x858000010001000000000669636c6f756403636f6d0000010001c00c000100010000105a00044d583737>
```

Это захардкоженный DNS-запрос к `icloud.com`: по умолчанию трафик маскируется
под обращение к Apple.

Список заставляет движок **сгенерировать I1 заново** под другой протокол, чтобы
трафик выглядел как что-то ещё, что сеть точно пропускает:

| Вариант | Подо что маскируется |
|---|---|
| (не генерировать) | встроенный запрос к icloud.com |
| QUIC | ClientHello от QUIC-соединения |
| DNS | DNS-запрос с padding-записью EDNS0 |
| SIP | пакет SIP-телефонии |
| STUN | STUN-пакет (WebRTC) |
| случайный | любой из четырёх выше, выбранный жребием |

Смысл появляется, когда сеть придирается именно к содержимому: DNS пропускают
везде, а к QUIC могут относиться иначе. Все четыре варианта — то, что
рекомендует сам гайд AmneziaWG: объёмный UDP, который уже пропускают все.

### I1-sni (хост для маскировки)

Хост, которым прикидывается сгенерированный I1. Работает **только вместе с
предыдущим пунктом** — при выключенной генерации ни на что не влияет.

Пусто — движок берёт один из четырёх: `www.apple.com`, `www.google.com`,
`www.microsoft.com`, `cdn.jsdelivr.net`. Своё значение стоит вписывать, если
знаете конкретный хост, который у вашего провайдера точно не режется.

### Свой I1

Ручной ввод init packet целиком, в формате `<r N><b 0x…>`. Для случая, когда
готовый I1 уже есть — например, выписанный из чужого рабочего конфига.
Заполненное поле **перебивает** и встроенный I1, и генерацию. Значение `none`
означает «не отправлять init packet вообще».

### Только порт

Cloudflare WARP отвечает на четырёх основных UDP-портах: **2408, 500, 1701,
4500**. При обычном скане движок сначала пробует их (фаза 1), находит открытые и
дальше работает с ними. Если не открылся ни один основной, он добавляет ещё
полсотни резервных (854, 859, 864 и далее) и пробует их.

Это поле закрепляет **один конкретный порт** и полностью пропускает фазу 1:
быстрее, но без гибкости. Если этот порт закрыт, рабочих эндпоинтов не будет
вовсе, хотя на других портах они есть. `0` — автоматический режим. Заполнять
стоит, только когда точно знаете, какой порт проходит.

### Полный перебор

По умолчанию движок берёт из каждой подсети столько адресов, сколько указано в
поле «Хостов на подсеть». Галочка игнорирует это поле и берёт **все 256 адресов
каждой подсети** (в коде — `sample = 0`):

- IPv4: 14 подсетей × 256 = **3584 адреса**;
- IPv6 (если включён следующий пункт): 2 подсети × 256 = **512 адресов**.

Для сравнения: при 100 в поле «Хостов на подсеть» выходит 1400 адресов и около
трёх минут. Полный перебор — дольше и без гарантии, что найдётся что-то
принципиально лучше. Это последний вариант, когда обычный скан ничего не дал.

### Использовать IPv6-пул

Переключает сканирование на IPv6-пулы. Адресов там два блока —
`2606:4700:d0::/48` и `2606:4700:d1::/48`. Смысл: некоторые провайдеры дают
IPv6, но режут IPv4 к Cloudflare, и это запасной обход. Для IPv6-скана у роутера
должен быть рабочий IPv6-адрес (либо включён warp-in-warp, где туннель несёт оба
семейства).

### Что на практике

Полезны в основном «Только порт», «Полный перебор» и IPv6 — и то как аварийные
варианты, когда обычный скан пуст. Обфускацию на обычной сети лучше не трогать:
встроенный I1 под iCloud и `6/10/50` уже проверены на роутере, а неудачно
подобранные junk-параметры дают ровно тот симптом, ради которого этот движок и
писался, — handshake проходит, а данные не идут.

## Сборка

Всё делается в WSL Ubuntu (Go обязателен линуксовый, см. грабли ниже):

```bash
# версия берётся из version.txt, формат ipk
wsl -d Ubuntu-26.04 -- bash -lc "cd <repo> && ./build.sh"
# явная версия + формат
./build.sh 0.3.1-r3 ipk
# только apk под 25.12
./build.sh apk
# оба формата
./build.sh 0.3.1-r3 both
```

Версия идёт по схеме **`x.y.z-rN`**: ревизия `r` растёт до 99, затем
увеличивается `z` и `r` сбрасывается в 1 (`0.3.1-r99` → `0.3.2-r1`).
`x` и `y` вручную не трогать — все правки одного цикла работы идут ревизиями.
Текущая серия: `0.3.1-rN`.

## Размер пакета

Движок — статический Go-бинарник с userspace-netstack (gVisor), это основная
часть веса. Сжатие UPX встроено в `build.sh` и применяется **к бинарнику до
упаковки в ipk**: ipk — это gzip-архив, и сжимать уже сжатое бессмысленно.

| | бинарник | ipk |
|---|---|---|
| без UPX | 12.6 МБ | 4.84 МБ |
| с UPX `--best --lzma` | 3.25 МБ | **3.39 МБ** |

Упакованный бинарник проверен на роутере полным сканом через userspace-туннели
(12/12 эндпоинтов, проверка Telegram, без паник), а не только запуском
`version`: UPX добавляет распаковщик, который выполняется до `main()`, и плохая
упаковка даёт сбой в рантайме, а не сборочную ошибку.

Собрать без сжатия — `NO_UPX=1 ./build.sh`. Если `upx` не установлен, сборка
не падает, а просто кладёт в пакет несжатый бинарник (в WSL: `apt install upx-ucl`).
После установки движок занимает 3.1 МБ в `/overlay` вместо 12 МБ.

Замер на этом роутере (2 ядра Cortex-A53, полный пул — 126 эндпоинтов,

| потоков | время | нагрузка |
|---|---|---|
| 8 | 68.6 с | 1.39 |
| 32 | 28.0 с | 1.55 |
| **64** | **21.9 с** | **1.26** |
| 128 | 25.1 с | 2.06 |
| 192 | 21.9 с | 3.41 |
| 256 | 25.2 с | 3.00 |

## Установка

```sh
opkg install --force-reinstall /tmp/luci-app-rrws_<ver>_all.ipk
# postinst сам делает rpcd reload
```

Учётные данные роутера в репозитории не хранятся: тестовые скрипты берут их из
переменных окружения (`ROUTER_HOST`, `ROUTER_USER`, `ROUTER_PASS`).

Проверка: `ubus call luci.rrws version`, `ubus call luci.rrws accountStatus`.

## Что переживает перезагрузку

| Файл | Переживает reboot | Переживает sysupgrade |
|---|---|---|
| `/etc/rrws-account.json` — аккаунт WARP | да | да |
| `/etc/rrws-settings.json` — настройки формы | да | да |
| `/etc/rrws-last-result.json` — результат последнего скана | да | да |
| `/tmp/rrws_result.json` — результат текущего запуска | нет | нет |
| `/tmp/rrws-state/` — pid, прогресс, логи | нет | нет |

Результат пишется в `/tmp` во время скана и копируется в `/etc` **сразу по
завершении** — тот же JSON, что показывает страница, включая колонку Telegram.
После перезагрузки страница отдаёт его как `saved: true`, и это же значение
переживает `sysupgrade` (файл перечислен в
`/lib/upgrade/keep.d/luci-app-rrws`).

Проверено на роутере: скан → `reboot` → все 205 эндпоинтов на месте, `/tmp`
пуст, `saved: true`. Прежде файл в `/etc` создавался только при старте
**следующего** скана (старый результат копировался перед перезаписью), поэтому
единственный скан терялся при первой же перезагрузке, а `keep.d` при этом
обещал обратное.

Настройки формы (`settings.json`) сохраняются при каждом нажатии «Найти
тоннели», так что после перезагрузки параметры скана остаются теми же.

## Диагностика на чужом роутере

Пакет помечен `Architecture: all` (он в основном скрипты), но несёт **бинарник
под aarch64 Cortex-A53**. На роутере с другим процессором установка пройдёт
успешно, файл появится — и движок не запустится. Внешне это выглядит как
«пакет ничего не делает», поэтому проверка встроена в три места:

**1. Сразу после установки** — `postinst` пишет в системный лог:

```sh
logread | grep rrws
# rrws: установлен: архитектура роутера aarch64_cortex-a53, движок работает: yes
```

**2. При попытке запуска скана** — вместо ложного `{"started": true}` приходит
внятная ошибка, а в лог уходит полный отчёт:

```
rrws: СБОЙ: движок не запускается (/usr/bin/rrws version не отвечает)
rrws:   архитектура роутера: 'aarch64_cortex-a53' / arch aarch64_cortex-a53 10
rrws:   пакет собран под: aarch64_cortex-a53 (mediatek/filogic, Cortex-A53)
rrws:   движок /usr/bin/rrws: есть
rrws:   движок version -> (пусто)
rrws:   права: -rwxr-xr-x 1 root root /usr/bin/rrws
rrws:   бэкенд: /usr/share/rpcd/ucode/luci.rrws есть
rrws:   аккаунт: /etc/rrws-account.json есть
rrws:   свободно на /overlay: ... / свободно в /tmp: ...
```

**3. В логе запуска** — что именно сканируется:

```
rrws: scanStart proto=awg perSubnet=6 total~6 jobs=8 timeout=3 tg=on tunPing=on speed=top10 port=auto targets=8.34.70.0/24
rrws: scanStart pid=23543 out=/tmp/rrws_result.json log=/tmp/rrws-state/scan.log
```

Порядок разбора при «не работает»:

1. `logread | grep rrws` — есть ли строка об установке и что в ней `движок работает:`
2. `/usr/bin/rrws version` — отвечает ли движок вообще
3. `ubus call luci.rrws scanStart` — текст ошибки прямо в ответе
4. `cat /tmp/rrws-state/scan.log` — что сказал движок, если он стартовал
5. `cat /tmp/rrws.rpc.log` — что и куда запускал бэкенд

## Грабли, оплаченные временем

1. **Windows-Go в PATH WSL даёт неработающий бинарник.** `/mnt/c/Program Files/Go/bin`
   перехватывает `go` раньше `/usr/local/go/bin`. Такой бинарник собирается и
   линкуется, но на Cortex-A53 падает с `Illegal instruction` (rc 132).
   `build.sh` ставит линуксовый тулчейн первым и отказывается собирать
   виндовым.

2. **`sed` по бинарнику его убивает.** Первая версия `build.sh` прогоняла
   `sed -i 's/\r$//'` по всему дереву пакета, включая ELF. В ELF есть байты
   `0x0D`, sed их вырезал — файл терял 279 байт и падал с SIGILL, оставаясь
   похожим на нормальную сборку. CRLF-очистка теперь только по текстовым
   файлам, бинарник ставится после неё.

3. **ucode не разрешает обращение вперёд — ни к функции, ни к константе.**
   `accountStatus` отдавал `Unknown error`, потому что звал `register_running()`,
   объявленную ниже по файлу. Хуже второй случай: `targets_from_excludes()`
   читала массив `SUBNETS`, объявленный на 28 строк ниже. `undefined` даёт
   `length() == 0`, цикл не выполнялся, функция возвращала `null` — а
   вызывающий код трактовал это как «исключений нет». Пользователь снимал
   галочки, а скан шёл по всему пулу, и внешне всё выглядело рабочим.
   В `luci.rrws` порядок «константы → вызываемые → вызывающие» проверяется
   скриптом (аудит должен покрывать и `const`, не только `function`).

4. **`E()` в LuCI принимает ровно ОДИН дочерний аргумент.** `E('tr', {}, td1, td2)`
   молча выбрасывает `td2` — так пропали значения ID/Address/Key, поля формы и
   кнопки. В `scan.js` узлы везде добавляются через `appendChild`.

5. **`rpc.declare`/`rpc.call` в LuCI молча шлют `{}`.** Объект-параметр до rpcd не
   доходит, запрос возвращает `200 OK` с пустым телом — внешне «сохранено», а
   файл настроек не меняется. Не помогли ни `params: {}`, ни `params: []`, ни
   маппинг имён, ни `nobatch`. Работает только **прямой POST** в `/ubus/`:

   ```js
   fetch('/ubus/', { method: 'POST',
     headers: { 'Content-Type': 'application/json' },
     body: JSON.stringify({ jsonrpc: '2.0', id: Date.now(), method: 'call',
       params: [L.env.sessionid, 'luci.rrws', 'saveOpts', opts] })
   }).then(r => r.json()).then(m => m.result[1]);
   ```

   Плюс: **не называть метод бэкенда `saveSettings`** — LuCI владеет этим именем
   (сабмит форм), и вызов уходит в функцию фреймворка. Метод называется `saveOpts`.

6. **Диагностика пустого сохранения:** `rpclog` в начале метода бэкенда, затем
   `cat /tmp/rrws.rpc.log`. Если лога нет — запрос не дошёл до rpcd, и проблема
   на клиенте, а не в ACL. Перехват `L.rpc.call` в браузере показывает
   *намерение*, а не факт: он логировал корректный payload, пока реальный запрос
   не отправлялся вообще.

7. **Поллинг скана обрывался на первом `running: false`.** Движок стартует через
   `setsid`, pidfile появляется не мгновенно. Первый опрос статуса читал
   `running: false`, страница считала скан завершённым и выходила из цикла —
   результат оставался старым, пока пользователь не перезагрузит страницу
   вручную. Это и была «минута тишины» после прогресс-бара.

   Исправлено с двух сторон: бэкенд ограниченно ждёт появления pidfile и
   проверяет `/proc/<pid>` (при неудаче возвращает ошибку, а не `started:true`),
   а фронтенд выходит из цикла только если скан уже видели живым либо прошёл
   grace-период 15 с.

   Отдельно: попытка «оптимизировать» это пустым циклом
   `while (!file_exists(PIDFILE))` **без sleep** даёт обратный эффект — цикл
   пролетает мгновенно, pidfile не успевает появиться, и каждая запись в лог
   врёт про «pidfile missing».

8. **`mkdir()` в ucode не создаёт каталог** и не сообщает об ошибке. Каталог
   состояния делается через `mkdir -p`.

9. **`-n` у движка — адресов НА ПОДСЕТЬ**, а не всего. UI спрашивает общее
   число; бэкенд пересчитывает (`per_subnet_sample`). Без этого «12 хостов»
   превращались в 168 проб и минуты скана.

10. **`pgrep` внутри rpcd-popен возвращает пусто** — pid берётся через
   `echo $$ > pidfile` в `setsid sh -c`.
